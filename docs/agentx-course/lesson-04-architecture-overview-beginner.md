# 第 4 课：整体架构图解读（小白版）

## 这节课要解决什么问题

前三课我们已经做了这些事：

1. 知道 AgentX 是一个智能体平台。
2. 用 Docker 把项目跑起来。
3. 从用户视角体验了前台和后台页面。

这一课开始理解系统背后的结构。

你之前看到过一张架构图，里面有很多框：

- Frontend Layer
- API Gateway Layer
- Core Business Services
- Infrastructure Layer
- External Integrations
- PostgreSQL
- RabbitMQ
- LLM Providers
- MCP Gateway

如果没有计算机基础，第一次看到这些词很容易懵。

所以这一课的目标是：

```text
不用背术语，先看懂这些框分别在系统里扮演什么角色。
```

## 先用餐厅理解架构

我们继续用餐厅做类比。

一家餐厅要正常工作，通常需要：

| 餐厅角色 | 作用 |
| --- | --- |
| 顾客 | 提出需求 |
| 菜单和点餐页面 | 让顾客选择和下单 |
| 服务员 | 接收顾客请求 |
| 厨房 | 真正做菜 |
| 仓库 | 保存食材 |
| 传菜员 | 传递任务和结果 |
| 外部供应商 | 提供额外食材 |
| 收银台 | 记录消费和付款 |

对应到 AgentX：

| 餐厅角色 | AgentX 里的角色 |
| --- | --- |
| 顾客 | 使用系统的用户 |
| 菜单和点餐页面 | 前端页面 |
| 服务员 | 后端 API |
| 厨房 | 核心业务服务 |
| 仓库 | 数据库 |
| 传菜员 | RabbitMQ 消息队列 |
| 外部供应商 | 大模型服务、MCP 工具服务、支付服务 |
| 收银台 | 计费和订单系统 |

所以架构图其实不是神秘东西。

它只是告诉我们：

```text
一个用户请求进入系统后，会被哪些部分处理。
```

## 一句话理解 AgentX 架构

AgentX 的整体结构可以简单理解为：

```text
用户在浏览器操作页面
  -> 前端把请求发给后端
  -> 后端组织业务流程
  -> 需要数据就查数据库
  -> 需要 AI 回复就调大模型
  -> 需要工具就调 MCP
  -> 需要异步处理就交给 RabbitMQ
  -> 最后把结果返回给前端页面
```

如果画成简单图：

```text
浏览器
  ↓
前端页面
  ↓
后端 API
  ↓
核心业务服务
  ↓
数据库 / 大模型 / 工具 / 消息队列 / 文件存储
```

## 架构图里的五大区域

你可以把架构图分成五块来看。

```text
1. Frontend Layer        前端层
2. API Gateway Layer     后端入口层
3. Core Business Services 核心业务服务层
4. Infrastructure Layer  基础设施层
5. External Integrations 外部集成层
```

下面逐个解释。

## 第一层：Frontend Layer 前端层

前端就是你在浏览器里看到的页面。

比如：

- 登录页面
- 探索页
- Agent 列表
- 聊天页面
- 后台管理页面
- 用户管理页面
- 工具管理页面
- 知识库页面

在 AgentX 里，前端项目目录是：

```text
agentx-frontend-plus
```

它使用的是：

```text
Next.js + React
```

你现在不用深入理解 Next.js 和 React。

先记住：

```text
前端负责“让用户看见和操作”。
```

前端不是真正的大脑。

它更像餐厅里的菜单、点餐机、收银界面。

用户点了按钮，前端会把请求发给后端。

## 前端能自己完成所有事吗

不能。

比如你点击“登录”，前端自己并不知道账号密码对不对。

它要问后端：

```text
这个邮箱和密码能不能登录？
```

比如你打开后台用户列表，前端自己也没有用户数据。

它要问后端：

```text
请把用户列表给我。
```

比如你和 Agent 聊天，前端自己也不会调用大模型。

它要把你的消息发给后端：

```text
请帮我处理这次对话。
```

所以：

```text
前端负责展示和交互。
后端负责真正处理业务。
```

## 第二层：API Gateway Layer 后端入口层

图里有一个：

```text
AgentX Backend
Spring Boot
Port 8088
```

这就是后端服务。

在你的电脑上，它的地址是：

```text
http://localhost:8088
```

健康检查地址是：

```text
http://localhost:8088/api/health
```

后端可以理解成餐厅里的服务员和总调度。

它负责：

- 接收前端请求
- 判断用户是否登录
- 判断有没有权限
- 调用对应业务模块
- 查询数据库
- 调用大模型
- 调用工具
- 返回结果给前端

## 为什么图里叫 API Gateway

API 可以理解成：

```text
前端和后端沟通的接口。
```

Gateway 是网关，意思是入口。

所以 API Gateway Layer 可以先理解为：

```text
所有前端请求进入后端的入口。
```

不过在这个项目里，它不是那种单独部署的专业网关服务。

它更像：

```text
Spring Boot 后端应用里的 API 入口。
```

对应源码大概在：

```text
AgentX/src/main/java/org/xhy/interfaces
```

这里有很多 Controller。

Controller 就是后端接收请求的地方。

## 第三层：Core Business Services 核心业务服务层

这一层是 AgentX 最重要的部分。

它是系统真正处理业务逻辑的地方。

图里可能会看到这些服务：

- UserDomainService
- AgentDomainService
- MessageDomainService
- RAGSearchService
- ToolDomainService
- PaymentAppService

如果用人话解释：

| 服务 | 它负责什么 |
| --- | --- |
| UserDomainService | 用户、登录、权限 |
| AgentDomainService | Agent 创建、配置、发布 |
| MessageDomainService | 聊天消息、会话、上下文 |
| RAGSearchService | 知识库检索 |
| ToolDomainService | 工具和 MCP 调用 |
| PaymentAppService | 支付、订单、计费 |

这一层就像餐厅的厨房、收银台、会员系统、库存系统。

它负责真正干活。

## 这些 Service 是独立软件吗

对新手来说，这里很容易误会。

图里的这些 Service 不一定是一个个单独运行的软件。

在 AgentX 这个项目里，它们大多是 Spring Boot 后端里的代码模块。

也就是说：

```text
它们不是很多个独立程序。
它们主要是同一个后端项目里的不同 Java 类和包。
```

你可以理解成一个公司里不同部门：

- 用户部门
- Agent 部门
- 对话部门
- 工具部门
- 知识库部门
- 计费部门

它们都在同一家公司里，只是负责的事情不同。

## 第四层：Infrastructure Layer 基础设施层

基础设施层负责“底层支撑”。

比如：

- 数据库
- 消息队列
- 文件存储
- Docker 容器管理
- 向量检索
- 网络通信

这些东西不直接面对用户，但系统离不开它们。

就像餐厅里的：

- 冰箱
- 仓库
- 电力
- 燃气
- 传菜系统
- 收银机

用户不一定看得见，但没有它们餐厅就无法运转。

## PostgreSQL 是什么

PostgreSQL 是数据库。

数据库可以理解成：

```text
系统的长期记事本。
```

AgentX 需要保存很多数据：

- 用户账号
- Agent 信息
- 聊天记录
- 工具信息
- 知识库信息
- 订单信息
- 计费记录
- 执行 trace

这些都需要存在数据库里。

否则你重启系统后，所有东西都会丢。

## pgvector 是什么

图里写的是：

```text
PostgreSQL + pgvector
```

PostgreSQL 是数据库。

pgvector 是 PostgreSQL 的一个扩展。

它的作用是：

```text
帮助系统做向量检索。
```

对小白来说，你可以先理解成：

```text
pgvector 可以帮助系统从知识库中找出和用户问题最相关的内容。
```

比如你上传了一份 100 页的文档。

用户问：

```text
这个系统怎么配置模型？
```

系统不会把 100 页都塞给大模型。

它会先用 pgvector 找出最相关的几段，再交给模型回答。

这就是 RAG 的基础。

## RabbitMQ 是什么

RabbitMQ 是消息队列。

这个词听起来很难，其实可以用快递站理解。

假设餐厅里有些任务不需要立刻完成，比如：

- 处理大文件
- 解析文档
- 生成向量
- 执行定时任务
- 发送通知

如果这些任务都让用户等着，页面会很卡。

所以系统可以先把任务放进 RabbitMQ：

```text
任务先排队
后台慢慢处理
处理完再更新状态
```

RabbitMQ 就像一个任务排队系统。

## 文件存储是什么

AgentX 里用户可能会上传文件，比如：

- PDF
- Word
- Markdown
- 图片
- 知识库文档

这些文件需要保存起来。

文件存储可以理解为：

```text
系统的文件柜。
```

数据库适合保存结构化信息，比如用户名、Agent 名称、订单状态。

文件存储适合保存真正的文件。

## DockerService 是什么

图里可能有：

```text
DockerService
Container Management
```

它和工具运行环境有关。

有些工具可能需要在独立容器里运行。

DockerService 就负责管理这些容器。

你暂时可以理解为：

```text
它负责给某些工具准备运行房间。
```

## 第五层：External Integrations 外部集成层

外部集成层表示：

```text
不在 AgentX 内部，但 AgentX 需要调用的外部服务。
```

图里常见的有：

- LLM Providers
- MCP Gateway
- Payment Gateways
- GitHub Integration
- API Premium Gateway

下面逐个解释。

## LLM Providers 是什么

LLM 是大语言模型。

Provider 是服务商。

LLM Providers 就是：

```text
提供大模型能力的服务商。
```

比如：

- OpenAI
- Anthropic
- 其他兼容 OpenAI 接口的平台
- 自己部署的模型服务

AgentX 自己不是大模型。

AgentX 更像一个平台：

```text
它负责组织 Agent、上下文、工具和知识库。
真正生成回答的是外部大模型。
```

## MCP Gateway 是什么

MCP 可以先理解为：

```text
一种让 AI 调用外部工具的方式。
```

MCP Gateway 就像工具中转站。

Agent 想调用工具时，不一定直接访问工具本身，而是通过 MCP Gateway 统一转发。

比如：

```text
Agent 想查某个外部系统
  -> 后端把工具调用发给 MCP Gateway
  -> MCP Gateway 找到对应工具
  -> 工具执行
  -> 结果返回给 Agent
```

这让工具管理更统一。

## Payment Gateways 是什么

Payment Gateway 是支付网关。

比如：

- 支付宝
- Stripe

AgentX 里有计费系统。

如果用户充值、购买套餐、支付订单，就可能需要调用支付网关。

你可以理解为：

```text
支付网关就是系统和支付平台之间的桥。
```

## API Premium Gateway 是什么

图里还有一个：

```text
API Premium Gateway
High Availability
Port 8081
```

它是可选组件。

它主要用于模型高可用。

高可用可以理解为：

```text
一个模型接口不稳定时，系统可以换别的接口继续服务。
```

比如你配置了多个模型渠道。

某个渠道失败了，网关可以尝试其他渠道。

新手阶段可以先知道：

```text
它是增强模型调用稳定性的可选服务。
```

不是理解主流程的第一优先级。

## 一次普通页面请求怎么走

比如你打开后台用户列表：

```text
http://localhost:3000/admin/users
```

大致流程是：

```text
浏览器打开后台页面
  ↓
前端页面加载
  ↓
前端向后端请求用户列表
  ↓
后端检查你是不是管理员
  ↓
后端查询数据库
  ↓
数据库返回用户数据
  ↓
后端把数据返回给前端
  ↓
前端把用户列表显示出来
```

这是一种普通业务请求。

## 一次聊天请求怎么走

聊天请求比普通页面请求复杂。

大致流程是：

```text
用户在聊天框输入问题
  ↓
前端把问题发给后端
  ↓
后端确认用户身份
  ↓
后端找到当前会话
  ↓
后端找到当前 Agent
  ↓
后端读取 Agent 的模型配置和提示词
  ↓
后端读取历史聊天记录
  ↓
如果有知识库，先做 RAG 检索
  ↓
如果有记忆，检索相关记忆
  ↓
如果有工具，准备工具列表
  ↓
后端调用外部大模型
  ↓
模型生成回答
  ↓
后端把回答流式返回给前端
  ↓
前端一点点显示回答
  ↓
后端保存聊天记录、token、trace
```

这条链路是后面课程最重要的主线。

## 为什么聊天要“流式返回”

你使用 AI 聊天时，回答通常不是等全部生成完才显示，而是一点点出现。

这叫流式返回。

好处是：

```text
用户不用等很久，能马上看到 AI 正在回答。
```

在 AgentX 中，后端通过类似 SSE 的方式，把模型生成的内容逐步推给前端。

你可以先理解为：

```text
后端一边收到模型输出，一边把内容传给前端页面。
```

## 架构图里的箭头怎么读

架构图里的箭头通常表示：

```text
谁调用谁
或者
数据从哪里流向哪里
```

比如：

```text
前端 -> 后端
```

意思是：

```text
前端向后端发请求。
```

```text
后端 -> PostgreSQL
```

意思是：

```text
后端查询或保存数据库。
```

```text
后端 -> LLM Providers
```

意思是：

```text
后端调用外部大模型。
```

不要把箭头看成很复杂的东西。

先用一句话理解：

```text
箭头就是请求或数据的流动方向。
```

## 端口在架构里的作用

你已经见过这些端口：

| 端口 | 服务 |
| --- | --- |
| 3000 | 前端页面 |
| 8088 | 后端 API |
| 5432 | PostgreSQL |
| 5672 | RabbitMQ |
| 15672 | RabbitMQ 管理页面 |
| 8081 | 可选 API 网关 |

端口就是访问不同服务的门牌号。

比如：

```text
localhost:3000
```

找的是前端。

```text
localhost:8088
```

找的是后端。

## 为什么架构要分层

你可能会问：

```text
为什么不能所有东西都写在一起？
```

因为项目一旦变大，混在一起会很难维护。

分层的好处是：

```text
前端只管显示页面。
后端入口只管接请求。
业务服务只管业务规则。
数据库只管保存数据。
外部服务只管提供外部能力。
```

每一层负责自己的事情，系统会更清晰。

这就像餐厅：

- 服务员不要跑去管理冰箱电路
- 厨师不要跑去做收银系统
- 收银员不要跑去切菜

职责分清，系统才不会乱。

## 对新手最重要的理解

现在不需要你掌握所有技术。

你只要先记住这张简化图：

```text
用户
  ↓
前端页面
  ↓
后端服务
  ↓
业务模块
  ↓
数据库 / 大模型 / 工具 / 文件 / 消息队列
```

以后每看到一个功能，都可以问：

```text
这个功能的前端页面在哪里？
它调用了哪个后端接口？
后端用了哪个业务模块？
数据存在哪里？
有没有调用外部服务？
```

这就是读源码的思路。

## 本课小结

这一课我们把架构图拆成了几块：

```text
Frontend Layer：前端页面，给用户看和操作。
API Gateway Layer：后端入口，接收前端请求。
Core Business Services：核心业务服务，真正处理业务。
Infrastructure Layer：基础设施，数据库、消息队列、文件存储等。
External Integrations：外部服务，大模型、工具、支付等。
```

你可以用一句话记住：

```text
前端负责看见，后端负责处理，数据库负责保存，大模型负责生成回答，工具负责扩展能力。
```

AgentX 的架构不是为了复杂而复杂。

它之所以有这么多模块，是因为它不只是一个聊天框，而是一个完整的 Agent 平台。

第 5 课会进入代码目录导览。

下一课会讲：

- 项目根目录下有哪些文件夹
- 前端代码在哪里
- 后端代码在哪里
- 文档在哪里
- Docker 部署文件在哪里
- 数据库脚本在哪里
- 初学者应该先看哪些文件，不应该先看哪些文件

从第 5 课开始，我们会正式打开代码地图，为后面阅读源码做准备。

# hi Agent 首阶段规格：可恢复的单 Agent 运行

依据 2026-10-14 的产品决策与既有重构方案编写。本文使用项目术语表中的 Agent、目标、运行、步骤、MCP 服务和工具动作。首阶段的可复现示例是“检索使用者上传的项目资料，生成有依据的草稿，经有效审批策略允许后创建 GitHub Issue”。本规格定义设计与验收；实施状态以 GitHub Issues #2–#21 为准。

## Problem Statement

作为自行部署 hi Agent 的开发者或小团队，我可以配置 Agent 并接入知识与工具，但目前难以确信 Agent 会可靠地完成一次真实工作：同一会话中的不同目标缺少独立运行记录；自动工具调用缺少明确的写入审批边界；审批等待、进程重启和外部写入结果不明时没有可恢复、可核对的工作状态；轨迹和自动评测也不足以证明结果有依据且没有越权写入。功能入口多于已经验证的端到端能力，使我难以判断平台可以放心用于哪类工作。

## Solution

保留自然语言配置 Agent 和现有自部署技术栈，以一次目标对应一次运行的持久执行模型串起 Web 控制台、知识检索、MCP 工具动作、使用者授权、审批、结果与轨迹。创建者定义 Agent 和审批策略；使用者用自己的 GitHub 身份限定仓库，可为单次运行收紧审批。Agent 先检索已上传资料并提供可核查引用，再提出创建 Issue 的内容与目标仓库。平台按策略审批、执行并记录结果。等待审批和进程重启后可以恢复；外部写入结果不明时先核对，只有确认未发生写入才自动重试，否则等待人工核对。

首阶段交付一条可在全新自部署环境自动复现的单 Agent 闭环，以及围绕依据、权限、恢复和重复写入的评测与测试。

## User Stories

1. As an Agent 创建者, I want 用自然语言定义 Agent 的职责和指令, so that 我可以直接表达要它完成的工作。
2. As an Agent 创建者, I want 为 Agent 选择现有的 OpenAI 兼容或 Anthropic 模型连接, so that 我可以沿用已支持的模型协议。
3. As an Agent 创建者, I want 看见每个 MCP 服务及其提供的工具动作, so that 我能分别管理连接与具体能力。
4. As an Agent 创建者, I want 为 Agent 选择允许调用的工具动作, so that 运行只接触我明确开放的能力。
5. As an Agent 创建者, I want 看见工具动作的写入分类和审批要求, so that 我能理解每项动作的风险边界。
6. As an Agent 创建者, I want 默认要求外部写操作逐次审批, so that 新增写入能力不会自动获得执行权限。
7. As an Agent 创建者, I want 逐项预授权特定工具动作, so that 低风险且已审查的动作可以自主执行。
8. As an Agent 创建者, I want 撤销工具动作的预授权, so that 后续运行重新要求审批。
9. As an Agent 创建者, I want 发布可引用的 Agent 版本, so that 已开始的运行不受之后编辑影响。
10. As an Agent 创建者, I want 在控制台配置知识库与工具动作, so that Agent 的可用资料和能力对我可见。
11. As a 使用者, I want 上传项目资料并看到索引是否就绪, so that 我知道运行何时能检索这些资料。
12. As a 使用者, I want 连接自己的 GitHub 身份, so that Issue 以我的授权身份创建。
13. As a 使用者, I want 指定这次连接可写的仓库, so that Agent 无法写入其他仓库。
14. As a 使用者, I want 撤销外部连接授权, so that 尚未执行的写操作立即失去权限。
15. As a 使用者, I want 在已有会话中提出新的目标, so that 连续讨论仍能保留上下文。
16. As a 使用者, I want 每个目标生成独立的运行编号和状态, so that 我能区分同一会话中的多次工作。
17. As a 使用者, I want 为本次运行设置比创建者要求更严格的审批, so that 我能控制自己的授权风险。
18. As an Agent 创建者, I want 使用者无法放宽我设置的审批策略, so that Agent 的权限边界保持有效。
19. As a 使用者, I want 运行固定 Agent、工具目录和知识版本, so that 中途改配置不会改变这次工作的依据。
20. As a 使用者, I want Agent 从我上传的资料中检索相关内容, so that Issue 草稿针对我的项目事实。
21. As a 使用者, I want 在草稿中看见可核查的资料引用, so that 我能判断内容是否有依据。
22. As a 使用者, I want 在资料不足时收到明确提示, so that 我不会把缺乏依据的内容误认为已核实。
23. As a 使用者, I want 在写入前看见 Issue 标题、正文、目标仓库和工具动作, so that 我知道将发生什么。
24. As a 使用者, I want 批准一项待执行写操作, so that 平台只执行我确认过的内容与目标。
25. As a 使用者, I want 拒绝一项待执行写操作, so that 该操作不会写入外部系统。
26. As a 使用者, I want 已预授权且仍在仓库授权范围内的动作无需额外点击, so that 合规的任务可以自动完成。
27. As a 使用者, I want 刷新浏览器后仍能查看待审批运行, so that 页面断开不会丢失工作。
28. As a 使用者, I want 服务重启后继续处理待审批运行, so that 人工等待不依赖某个进程存活。
29. As a 使用者, I want 看到运行的步骤、当前状态和失败原因, so that 我知道工作进展和需要处理的事项。
30. As a 使用者, I want 完成后看到创建的 Issue 链接与所引用的资料, so that 我能检查最终结果。
31. As a 使用者, I want 取消仍在进行的运行, so that 后续未执行的动作不会继续发生。
32. As a 使用者, I want 别人不能查看或审批我的运行, so that 我的资料和外部授权受到保护。
33. As a 使用者, I want 运行中途的 Agent 配置更新只影响新运行, so that 已开始的运行结果可解释。
34. As a 使用者, I want 连接授权在实际写入前再次核验, so that 运行开始后的撤权仍然生效。
35. As a 使用者, I want 已确认成功的写操作在队列重投时不再执行, so that 不会创建重复 Issue。
36. As a 使用者, I want 外部写入结果不明时先自动核对, so that 系统尽可能恢复而不盲目重试。
37. As a 使用者, I want 只有确认写入未发生时才自动重试, so that 自动恢复不会造成重复结果。
38. As a 使用者, I want 无法确认写入结果时看到待核对状态, so that 我可以检查外部系统后决定下一步。
39. As a 使用者, I want MCP 服务接口与本次固定的工具结构不兼容时暂停运行, so that 配置变化不会改变实际执行的动作。
40. As a 使用者, I want 未授权仓库和未经批准的工具动作被拒绝, so that 模型的请求不能越过平台策略。
41. As an Agent 创建者, I want 为新 MCP 连接使用 Streamable HTTP, so that 我能接入当前主流的远程 MCP 服务。
42. As an Agent 创建者, I want 在迁移期继续使用已有 SSE 连接, so that 现有集成有时间迁移。
43. As an Agent 创建者, I want GitHub Issue 示例经通用 MCP 工具动作运行, so that Agent 核心不依赖 GitHub 专有调用。
44. As a 平台运维者, I want PostgreSQL 保存运行权威状态、RabbitMQ 只派发工作, so that 服务重启和重复消息可恢复。
45. As a 平台运维者, I want 轨迹记录审批决定、工具结果、失败原因及模型用量, so that 我能诊断运行并评估成本。
46. As a 平台运维者, I want 普通日志与使用者可见轨迹不暴露外部凭据, so that 故障排查不泄露密钥。
47. As a 平台运维者, I want 在全新自部署环境重放 GitHub Issue 示例, so that 我能验证部署是否可用。
48. As a 平台运维者, I want 自动测试覆盖重启、重复投递、拒绝审批和结果不明, so that 可靠性可以持续验证。
49. As a 产品维护者, I want 用版本化评测样例检查资料引用、Issue 内容、工具选择和失败处理, so that 每次改动有可比较的质量证据。
50. As a 产品维护者, I want 默认导航只展示已验证的能力并标明未完成的功能, so that 使用者不会把概念性功能当作可用能力。
51. As a 项目维护者, I want README 与项目源码统一标注 MIT 和 KumiKo2007 的版权声明, so that 项目许可清楚一致。

## Implementation Decisions

- 保留 Java 17、Spring Boot、Next.js、PostgreSQL 和 RabbitMQ。首阶段复用现有部署形态，不加入独立工作流服务。
- 目标是使用者交办的结果；一次运行只处理一个目标；会话承载连续交流且可包含多次运行。步骤是运行内部动作；定时任务仅指未来的自动触发配置。
- 新运行入口返回独立运行标识和当前状态。公开接口允许按权限读取运行、步骤、审批请求、结果及同一会话的运行列表，并提交审批决定或取消请求。实时推送只用于展示；断线后从持久状态重新读取。
- 运行的权威记录至少包含所有者、会话、目标、状态、固定的 Agent/工具/知识版本、创建与更新时间、结果或失败原因；步骤记录顺序、动作类型、状态、时间和可审计结果。审批请求记录待执行的工具动作、目标资源、固定参数、策略判定及决定者与决定时间。
- 运行状态至少区分 `PENDING`（待执行）、`RUNNING`（运行中）、`WAITING_APPROVAL`（待审批）、`WAITING_RECONCILIATION`（待核对）、`WAITING_SCHEMA_REVIEW`（工具结构待核对）、`COMPLETED`（完成）、`FAILED`（失败）与 `CANCELLED`（取消）。当模型请求时展示的冻结动作结构与当前目录或远端 MCP 结构不一致时，运行必须持久化暂停为 `WAITING_SCHEMA_REVIEW`，向使用者展示安全、明确的原因，且不调用该工具；检查并更新动作定义后，应通过新的运行重新执行。审批拒绝必须终止该待写动作并形成可见的非成功结果；取消阻止尚未开始的后续动作。服务重启后的工作领取依据数据库状态，而非内存中的 SSE 连接。
- PostgreSQL 负责提交运行与步骤状态；RabbitMQ 可重复投递同一工作。派发与领取机制必须能从数据库恢复漏发工作，并防止两个工作者同时推进同一状态；重复消息只能重读或推进同一运行，不能重复已确认成功的外部写入。
- 模型只提出工具动作。平台的统一执行边界在实际调用前验证 Agent 可用动作、工具参数结构、创建者审批策略、使用者对本次运行的收紧、使用者连接授权和目标资源范围。不能依赖模型文本或 MCP 服务自报元数据授予写入权。未知或无法可靠分类的外部动作按需审批的写操作处理。
- 默认所有外部写操作需要审批；创建者可对具体工具动作预授权，使用者只能收紧。批准绑定单次固定的动作、参数和目标资源；参数或资源变化必须重新判定与审批。连接授权是独立条件，预授权不能替代使用者的 GitHub 仓库授权。
- 使用者以自己的 GitHub 身份连接并限定仓库。执行前再次检查连接仍有效且仓库仍在范围内；运行固定配置不固定可撤销的身份授权。凭据只在受信任的连接执行边界使用，不进入模型上下文、普通轨迹或日志。
- 运行开始时固定 Agent 定义、已登记的工具目录与参数结构、知识版本。第三方 MCP 服务的实现不可冻结；若实际接口与固定结构不兼容，暂停并报告，不使用变化后的结构继续写入。
- 明确区分 MCP 服务与工具动作。新连接以 Streamable HTTP 为目标，旧 SSE 在迁移期通过适配层保留；具体 SDK 版本以稳定互通测试选择。GitHub 示例使用通用 MCP 执行边界，GitHub 特有的账号连接与结果核对能力留在连接适配层，不进入 Agent 运行核心。
- 知识库上传资料需要可见的处理状态。运行引用已固定且可检索的资料版本；草稿和结果保留可打开的来源标识。资料不足时明确告知，不伪造引用，也不自动执行缺乏依据的示例写入。
- 写入前持久记录唯一动作标识、目标与固定参数；写入成功后持久记录外部资源标识与结果。恢复时先查询已有结果。外部结果不明时先按动作标识或其他可验证证据核对；只有明确证明未写入时可自动重试。搜索不到 Issue 本身不是未写入的证明；若无法确认，运行进入待核对，不盲目重复创建。
- 运行轨迹按运行标识组织，含关键步骤、审批、工具调用、资料引用、模型用量及失败原因。使用者可见信息与运维日志均应按权限过滤敏感参数和凭据。
- Web 控制台串起 Agent 配置、资料上传、个人连接与仓库授权、发起运行、审批、查看结果和轨迹；隐藏未验证的外围入口或明确标注开发状态。
- 首阶段将项目源码及根许可证统一为 MIT，版权人写 KumiKo2007；第三方文件的原有许可头和第三方依赖许可仍保留。

## Testing Decisions

- 好测试只断言从公开接口或 Web 控制台能观察到的行为及外部副作用，不绑定内部类、状态机实现细节或某个队列时序。断言要覆盖“产生了什么”和“没有发生哪些不允许的写入”。
- 主要自动化测试边界是公开的运行 HTTP 接口，经真实 PostgreSQL 持久化和工作派发，使用确定性的模型响应与可控 MCP 服务替身。测试从提交目标开始，读取运行结果与轨迹，并观察 MCP 端实际收到的调用次数、参数和目标仓库。
- 一条浏览器端到端用例覆盖 Agent 配置、上传资料、连接测试身份、提出目标、查看引用与待审批内容、审批、查看 Issue 链接和步骤轨迹；另有拒绝审批及仓库越权的浏览器或接口用例。
- 后端测试覆盖同一会话多次运行、固定版本、审批策略合成、使用者撤权、跨重启审批、取消、重复队列消息、写入成功后重投、写入结果不明时核对成功/确认未写入/仍不确定三种分支，以及 MCP 新旧传输和接口变化。
- 外部集成测试以受控 GitHub 测试仓库或等价可观测 MCP 服务验证实际创建；故障注入测试在请求发出但响应丢失的时点重启工作者，以验证不会盲目重试。
- 版本化评测样例至少覆盖正确引用资料、Issue 标题和正文质量、目标仓库与工具选择、拒绝越权写入、资料不足与工具失败；记录通过率、耗时和成本。评测使用固定输入与可比较的评分准则，不把随机模型输出的精确措辞当断言。
- 现有后端有 Spring Boot/JUnit 服务级与集成测试，但会话测试中存在手工调用模型的代码，部分集成测试会无限等待；这些不是可靠的首阶段回归门槛。前端尚无默认自动测试脚本。新增测试应成为 PR CI 中可自动完成的测试，而不依赖手工输入密钥。
- PR 门槛包含后端测试、前端 lint/构建、端到端测试和权限/重复写入的关键性质测试。首个基线需先配置 JDK 与前端依赖，并修复不适合 CI 的既有测试。

## Out of Scope

- 多 Agent 编排、A2A、定时自动触发、多模态、SaaS 计费和工具市场的新功能。
- 新的专用模型服务商适配；首阶段稳定现有 OpenAI 兼容与 Anthropic 两类协议。
- 实时同步知识源的占位功能、跨会话长期记忆以及通用网页抓取。
- 保证任意第三方 MCP 写操作都具备无条件的“恰好一次”效果；缺少外部幂等支持或可验证核对证据时，必须暂停待核对。
- 冻结第三方 MCP 服务在运行期间的实际代码，或承诺旧 SSE 永久保留。
- 为不存在的线上数据或对外 API 兼容承诺设计迁移；仍需为本次数据模型与界面更新提供可执行的本地升级步骤。

## Further Notes

- 验收以全新自部署环境中的可复现 GitHub Issue 示例和自动评测为准，而非新功能数量。真实写入只使用明确授权的测试仓库。
- 不可写入条件包括：未获连接授权、仓库不在范围内、策略要求审批但尚未批准、审批被拒、工具结构与固定版本不兼容，以及资料不足却试图自动发布本示例内容。
- 关键恢复验收包括：审批等待跨重启保留、已确认成功的写操作不因重投而重复、结果不明时先核对、仅在可证明未写入时自动重试。
- 当前设计基于仓库 master 的 1ef0f3e。实施顺序由既有重构方案确定：建立基线，拆出运行核心，接入受控工具调用，完成 Web 示例闭环，最后收紧 CI 与评测门槛。
